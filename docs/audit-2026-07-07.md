## A. セキュリティ / 不正利用耐性（優先度: 高）

### A-1. 検索の PostgREST フィルタ注入
`lib/data/search.ts` の `searchThreads` / `searchReviews` がユーザー入力を
`.or(\`title.ilike.%${q}%,...\`)` に直接埋め込んでいる。`,` `(` `)` を含む検索語で
フィルタ構文が壊れ、検索破壊や条件改変が可能。→ 特殊文字のエスケープ必須。

### A-2. レート制限・モデレーションがアプリ層のみで、DB直叩きで全バイパス可能
`discussion_posts`(anyone can post anonymously)、`review_comments`、`reactions`、
`discussion_poll_votes` の RLS insert が `with check (true)`。公開されている anon キーで
PostgREST を直接叩けば `checkRateLimit` / `checkContent` を完全に迂回してスパム投稿できる。
さらに `checkRateLimit` は RPC 失敗時 fail-open。
→ 挿入を security definer RPC 経由に限定するか、trigger で `check_rate_limit` を DB 側で強制。

### A-3. view_count（人気順・Hot・注目の根拠値）が自由に水増し可能
`increment_thread_views` RPC は誰でも実行可能で、重複排除はクライアント制御の cookie のみ。
curl ループで人気順・トレンドスコア(view_count×0.15)を操作できる。
→ RPC に voter_key/時間窓ベースのサーバー側 dedup を追加。

### A-4. パスワードリセットURLの Host ヘッダ注入
`app/login/actions.ts` の `getSiteUrl()` が `x-forwarded-host` を無条件で信頼。
偽装ヘッダ付きリセット要求で攻撃者ドメインのリンクをメールに載せられる余地
(Supabase 側の redirect allowlist が最後の砦)。→ 本番は `NEXT_PUBLIC_SITE_URL` を優先。

### A-5. レビュー投稿(submitAlbumReview)にレート制限なし
スレ・コメント・リアクション等は保護済みだがレビュー本体のみ未保護。

### A-6. なりすまし可能な匿名名 + 投稿者ID不在
匿名投稿の表示名は自由入力のため、他ユーザーや管理者の表示名を騙れる。
ログイン投稿でも `discussion_posts` に author_id が保存されない。

## B. スキーマ / 設計上の欠陥（優先度: 高〜中）

### B-1. discussion_posts に author_id が無い【最重要の構造欠陥】
影響: ①自分の投稿を削除できない(削除は管理者のみ) ②返信先への通知が実装不可能
(コード内コメントで明記) ③ユーザーページに発言履歴を出せない ④BANの根拠が取れない。
→ author_id(nullable) 追加 + 5ch式のスレ内ID(voter_key由来のハッシュ)表示が本質的解決。

### B-2. NGワードがコードの空定数
`lib/moderation.ts` の `BANNED_PATTERNS: RegExp[] = []`。語を足すたびにデプロイが必要。
→ DBテーブル + 管理画面で運用。あわせて BAN(user_id / voter_key)機構が存在しない。

### B-3. 投票の一意性が cookie 依存
cookie 消去で何度でも再投票可能。匿名サイトの宿命だが、IPハッシュ併用等の緩和は可能。

### B-4. migrations の適用順が不定
ファイル名に番号プレフィックスが無く(`add_*.sql` 38本)、依存関係が暗黙。
`apply_pending_safe.sql` のような後追い修正ファイルも混在。データ修正SQL
(fix_ohtaki_album 等)とスキーマ変更が同居。→ 命名規約 + README を整備。

### B-5. DB型定義が手書き
`lib/supabase/types.ts` を手で維持しており実DBとの乖離リスク。`supabase gen types` 導入推奨。

## C. パフォーマンス（優先度: 中）

### C-1. 主要ページ全てが force-dynamic でキャッシュゼロ
ホームは1リクエストで10クエリ超。匿名閲覧が大半のコンテンツサイトなのに
ISR/`unstable_cache` が皆無(artists詳細のみ revalidate 3600)。DB負荷とTTFBに直撃。

### C-2. 期間別ランキングが全件取得→JS集計
`getTopRatedAlbumsByReviewPeriod` が期間内レビューを全行フェッチ。レビュー数万件で破綻。
→ SQL の group by / RPC 化。カテゴリフィルタ(limit×8取得→JS絞り込み)も同様。

### C-3. スレッドの投稿が全件ロード
`getDiscussionPostsByThreadId` にページネーションなし。5ch型で1スレ数百〜千レスに
なると詳細ページが重くなる一方。→ ページネーション or 1000レス上限(5ch式「レス落ち」)。

### C-4. 検索フォールバックが artists 全件スキャン
RPC未適用環境ではオートコンプリートの1キーストロークごとに全アーティスト取得。
`/api/search` 自体にレート制限もない。

## D. 機能ギャップ（サイト目的との照合、優先度: 中〜低）

### D-1. ランキングが単純平均 → 評価1件のアルバムが1位になれる
RYM型サイトの信頼性の核。ベイズ加重平均(例: (v·R + m·C)/(v+m))の導入が必須級。

### D-2. スレッドに「板」/カテゴリ/タグが無い
現状スレ一覧は単一リスト。スレ数が増えると発見性が崩壊する。5chの板に相当する
軽量なカテゴリ(邦楽/洋楽/ジャンル別/雑談等)が必要。

### D-3. モデレーション運用機能の不足
通報→管理画面はあるが、BAN・NGワード運用・スレ凍結など「処分」の手段がない。

### D-4. フォローフィードの不在
フォロー機能はあるが「フォロー中ユーザーの新着レビュー/スレ」を見る場所が薄い。
ソーシャルグラフが定着に寄与しない。

### D-5. 細かい改善候補
- レビュー一覧のソート(参考になった順等)
- 匿名⇔ログインの投稿使い分けUIの明確化(A-6と連動)
- reviews.created_at が date 型(時刻精度なし)で並び順が日単位
